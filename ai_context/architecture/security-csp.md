# Content Security Policy (CSP)

## Overview

Primer implements Content Security Policy (CSP) headers to protect against Cross-Site Scripting (XSS), clickjacking, and other code injection attacks. CSP is configured in both the Next.js middleware and the `next.config.ts` file.

## Implementation

### Files
- `/src/lib/csp.ts` - CSP configuration module
- `/src/middleware.ts` - Applies CSP headers via middleware
- `/next.config.ts` - Applies CSP headers via Next.js config (backup for static files)

### CSP Directives

#### `default-src 'self'`
Only allow resources from the same origin by default.

#### `script-src 'self' 'unsafe-inline' ['unsafe-eval' in dev]`
- `'self'` - Allow scripts from same origin
- `'unsafe-inline'` - Required for Next.js inline scripts and hydration
- `'unsafe-eval'` - Only in development mode for Hot Module Reloading (HMR) and webpack

**Note:** While `'unsafe-inline'` is generally discouraged, it's currently required for Next.js to function properly. Future improvements could use nonces or hashes for better security.

#### `style-src 'self' 'unsafe-inline' https://gail.wharton.upenn.edu`
- `'self'` - Allow styles from same origin
- `'unsafe-inline'` - Required for Tailwind CSS and dynamic styles
- `https://gail.wharton.upenn.edu` - External Wharton brand fonts CSS

#### `font-src 'self' data: https://gail.wharton.upenn.edu`
- `'self'` - Local fonts (Fira Code in `/public/fonts/`)
- `data:` - Inline font data URIs
- `https://gail.wharton.upenn.edu` - Wharton brand fonts (Acumin Pro, Minion Pro)

#### `img-src 'self' data: blob:`
- `'self'` - Same-origin images
- `data:` - Base64 encoded images (AI-generated images saved as artifacts)
- `blob:` - Blob URLs for dynamically generated content

#### `connect-src 'self' https://api.openai.com ws: wss: [localhost in dev]`
- `'self'` - Same-origin API calls
- `https://api.openai.com` - OpenAI API endpoints (Realtime API, Responses API, etc.)
- `ws:` and `wss:` - WebSocket connections for Socket.io (real-time features)
- `ws://localhost:*`, `wss://localhost:*`, `http://localhost:*` - Development mode HMR

#### `media-src 'self'`
Only allow audio/video from same origin.

#### `object-src 'none'`
Block all plugins (Flash, Java, etc.).

#### `base-uri 'self'`
Restrict `<base>` tag to same origin.

#### `form-action 'self'`
Only allow form submissions to same origin.

#### `frame-ancestors 'none'`
Prevent the site from being embedded in iframes (clickjacking protection).
Works in conjunction with `X-Frame-Options: SAMEORIGIN`.

#### `frame-src 'none'`
Block all iframes (unless needed for specific features).

#### `worker-src 'self' blob:`
Allow web workers from same origin and blob URLs.

#### `manifest-src 'self'`
Allow PWA manifest from same origin.

## External Resources

### Fonts
The application loads external fonts from Wharton's CDN:
- Domain: `https://gail.wharton.upenn.edu`
- Path: `/wp-content/plugins/martech-chupacabra/includes/fonts/`
- Fonts: Acumin Pro (regular, bold, black, condensed variants), Minion Pro (regular, bold)

These are whitelisted in both `style-src` and `font-src` directives.

### AI-Generated Images
Images generated by OpenAI DALL-E or Google Imagen are:
1. Generated via API calls to `/api/openai/generate-image`
2. Saved as artifacts (base64 or local files)
3. Served from same origin (not external URLs)

Therefore, no external image sources need to be whitelisted.

### WebSocket Connections
Socket.io is used for real-time communication:
- Same-origin WebSocket connections
- Protocols: `ws:` (development) and `wss:` (production)
- No external WebSocket servers

## Development vs Production

### Development Mode
- `'unsafe-eval'` is enabled for webpack HMR
- Localhost WebSocket connections allowed (`ws://localhost:*`, `wss://localhost:*`, `http://localhost:*`)
- More permissive for development tools
- Socket.io connects to `http://localhost:3000`

### Production Mode
- `'unsafe-eval'` is disabled
- Stricter policies
- Only necessary external resources allowed
- WebSocket URLs derived from `NEXT_PUBLIC_SOCKET_SERVER_URL` environment variable
- Example: If `NEXT_PUBLIC_SOCKET_SERVER_URL=https://your-app.onrender.com`, CSP will allow:
  - `wss://your-app.onrender.com` (WebSocket)
  - `https://your-app.onrender.com` (Socket.io polling fallback)

### Required Environment Variables

#### Production
- `NEXT_PUBLIC_SOCKET_SERVER_URL` - Your production domain (e.g., `https://your-app.onrender.com`)
  - Used for Socket.io WebSocket connections
  - Automatically added to CSP `connect-src` directive
  - Must be set before build time (NEXT_PUBLIC_* vars are embedded at build)

#### Development
- No additional environment variables needed
- Defaults to `http://localhost:3000`

## Security Considerations

### Mermaid Diagrams
- Mermaid library generates SVG diagrams dynamically
- Uses `dangerouslySetInnerHTML` to render SVG
- SVG content is sanitized via `/src/app/lib/security/html-sanitizer.ts`
- Sanitizer removes:
  - `<script>` tags
  - Event handlers (`onclick`, `onerror`, etc.)
  - `javascript:` protocol
  - Dangerous data URIs

### Dynamic React Components
The application may need to execute dynamically created React components in the future (e.g., via react-runner). This would require:
- Careful sandboxing
- Potentially relaxing `script-src` for specific routes
- Additional security measures

Currently, no dynamic code execution (`eval`, `Function()`) is used in the codebase.

### Proxy Route
The `/api/proxy` route can fetch external URLs but includes:
- URL validation via `/src/app/lib/security/url-validation.ts`
- SSRF (Server-Side Request Forgery) protection
- Rate limiting
- Zod schema validation

## Testing CSP

### Browser Console
1. Open browser DevTools
2. Check Console for CSP violations
3. Look for messages like: `Refused to load... because it violates the following Content Security Policy directive`

### HTTP Headers
Check response headers using browser DevTools Network tab or curl:

```bash
curl -I http://localhost:3000
```

Look for the `Content-Security-Policy` header.

### CSP Reporting (Future Enhancement)
Consider adding `report-uri` or `report-to` directives to collect CSP violation reports:

```
report-uri /api/csp-report;
```

This would help identify and fix CSP issues in production.

## Troubleshooting

### Common Issues

#### External Resource Blocked
If a legitimate external resource is blocked:
1. Identify the resource type (script, style, image, etc.)
2. Add the domain to the appropriate CSP directive in `/src/lib/csp.ts`
3. Rebuild and test

#### Next.js HMR Not Working
Ensure development mode is properly detected:
- Check `NODE_ENV=development`
- Verify `'unsafe-eval'` is in `script-src`
- Verify localhost WebSocket connections are allowed

#### Inline Styles/Scripts Blocked
- Inline styles: Already allowed via `'unsafe-inline'` in `style-src`
- Inline scripts: Already allowed via `'unsafe-inline'` in `script-src`
- For better security, consider using nonces or hashes instead

## Future Improvements

1. **Nonce-based CSP**: Use cryptographic nonces for inline scripts instead of `'unsafe-inline'`
2. **CSP Reporting**: Implement `report-uri` to collect violation reports
3. **Stricter Policies**: Remove `'unsafe-inline'` where possible
4. **Per-Route CSP**: Different CSP policies for different routes (e.g., admin vs public)
5. **Subresource Integrity (SRI)**: Add integrity attributes to external resources
