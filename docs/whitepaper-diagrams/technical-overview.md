# How Primer Works: Technical Overview

## The Runtime

Primer is a web application that serves as a runtime for AI-driven learning experiences. It does not contain educational content itself — it provides the infrastructure in which AI agents create, deliver, and assess that content. The platform is organized around a single core abstraction: the **Experience**, a self-contained, declarative configuration that fully describes an AI-mediated learning session without requiring any code changes to the platform.

Users interact with Primer through a browser. The interface presents a real-time voice conversation alongside a visual workspace — background scenes, informational slides, documents, and other artifacts appear in draggable, resizable windows managed by a unified window system. A live transcript runs alongside the conversation. The user speaks naturally into their microphone; the AI responds with expressive, low-latency voice synthesis. From the user's perspective, they are having a conversation with an intelligent character in an immersive environment. From the system's perspective, an AI agent is executing a prompt, calling tools, and coordinating with other agents to achieve pedagogical goals.

## Two Classes of Agent

Primer distinguishes between **front-end agents** and **backend agents**. Front-end agents run in the browser and maintain a persistent, real-time voice connection with the user. They are conversational — they listen, speak, and react. Backend agents run on the server, have no voice or direct user interaction, and are invoked programmatically by front-end agents through a delegation mechanism. Backend agents perform complex, multi-step tasks: analyzing transcripts, generating design documents, creating images, assembling new experiences. Both classes of agent share the same tool system and can read and write the same artifacts, but they occupy fundamentally different roles — front-end agents are performers; backend agents are stagehands.

A front-end agent can delegate work to a backend agent at any point during a conversation. When it does, the backend agent executes on the server while the user continues to see real-time status updates in the browser. The backend agent can even trigger visual changes on the user's screen — displaying slides, updating progress indicators — despite running entirely server-side. When the backend agent completes its task, the results (typically artifact identifiers) are returned to the front-end agent, which resumes the conversation.

## The Backend-First Tool Pattern

All agent capabilities in Primer are expressed as **tools** — discrete functions that agents can call to interact with the system. Tools cover a wide range of actions: displaying a slide, setting a background scene, playing a sound, creating or reading an artifact, conducting web research, delegating to another agent, logging a session event, and many more. Tools are organized into named **toolsets**, and each agent is assigned one or more toolsets that define its available capabilities.

The critical architectural decision is that all tool execution happens on the server, regardless of where the calling agent runs. When a front-end agent (running in the browser) calls a tool, the call is serialized and sent to the server over a persistent socket connection. The server validates the parameters, logs the invocation, and executes the tool implementation. If the tool has a visual effect — creating a slide, for instance — the server sends an event back to the browser, which renders the corresponding UI component. The browser confirms the result, the server relays it back, and the agent receives the outcome.

This round-trip may seem redundant for front-end agents, but it is deliberate. It means there is exactly one code path for every tool, whether called from the browser or the server. Logging, validation, authorization, and business logic are centralized. A new tool written once works for all agents in all contexts. Backend agents automatically gain the ability to trigger UI changes because the same socket-based communication channel is available to them. The pattern trades a small amount of latency for a large gain in architectural simplicity and extensibility.

## Communication Architecture

The socket connection between browser and server is bidirectional and carries several categories of traffic. **Tool calls** flow from agents (via the browser or directly on the server) to the tool execution engine. **UI events** flow from the server to the browser, instructing it to create, modify, or remove visual elements. **Delegation events** carry status updates and results between backend agent executions and the browser's progress overlay. **Tool results** flow back from the browser to the server when a UI-affecting tool completes its client-side work.

This socket layer is the nervous system of the application. It enables a programming model where any agent — front-end or backend, voice-interactive or silent — can observe the screen, create visual elements, read and write files, and coordinate with other agents, all through the same unified interface.

## The Experience as Configuration

An Experience is defined entirely by a directory of files, anchored by a JSON configuration. The configuration declares the experience's metadata (title, description, version, author), its AI provider profiles (mapping named roles to specific models and modalities), its agents (each with a name, voice, personality, type, AI configuration, toolset, and downstream handoff targets), its resources (scene images, sounds, pre-loaded artifacts), and its instruction files.

Instructions are the prompts that give each agent its identity and behavior. They are plain markdown files — one per agent — that describe the agent's role, personality, goals, conversational style, and a checklist of tasks to accomplish. Shared concerns (how to use tools, how to maintain a journal, how to handle errors, security guidelines) are factored into **supplemental instruction files** that are injected into agent prompts at runtime via placeholder resolution. This means an experience author can change an agent's entire personality by editing a single markdown file, without touching any code or any other agent's configuration.

The declarative nature of experiences is what makes the system extensible. The runtime has no foreknowledge of what any experience will do. It loads the configuration, resolves the instructions, connects the agents to their AI providers, and provides the tool infrastructure. Everything else — the pedagogical approach, the narrative arc, the characters, the assessment criteria — is defined in the experience files.

## Templates and Experience Generation

New experiences are not built from scratch. They are generated from **templates** — special experiences marked as such in their configuration. A template defines the structural skeleton: the agent flow (e.g., mentor, then practice, then feedback), the supplemental instruction files, the toolset assignments, and placeholder agent prompts with marked insertion points for customization. The current templates implement two pedagogical patterns — Roleplay (where the student practices interpersonal skills with an AI counterpart) and Teachback (where the student demonstrates mastery by teaching concepts to an AI learner) — but the template system is designed to accommodate any pattern. A future template might implement a Socratic dialogue, a collaborative problem-solving session, a simulation with branching narratives, or an entirely novel interaction model. The runtime imposes no constraints on what a template can define.

The generation process itself is orchestrated by a **meta-experience** — an experience whose purpose is to create other experiences. In the current implementation, the meta-experience is a voice conversation between an educator and an Intake Agent. The Intake Agent interviews the educator, then delegates to a pipeline of backend agents: a Design Agent that produces a structured design document, a Casting Director that customizes template prompts with specific characters, an Image Generation Agent that creates visual assets, and an Experience Builder that assembles the final product from a template. The entire pipeline communicates through artifacts — named files passed between agents by reference. The output is a new, complete, playable experience that the educator can test immediately.

This meta-experience is itself just an experience running on the same runtime. It uses the same tools, the same socket communication, the same agent delegation mechanism. There is nothing special about it architecturally — it simply happens to have agents whose job is to create other experiences rather than to teach students. This recursive quality is a natural consequence of the declarative, agent-driven architecture: if agents can do anything the tool system allows, and the tool system includes the ability to create and configure experiences, then agents can create experiences.

## Session Data and Analytics

Every interaction with an experience produces **session data**: conversation transcripts, journal entries written by agents, artifacts created during the session (slides, documents, checklists), and event logs. This data is stored per-session in the experience directory and is intentionally unstructured. The system captures everything — the full richness of the conversation — rather than reducing it to predefined metrics at capture time.

Analytics agents process this data after the fact. An experience can define a **Student Report Agent** that analyzes individual sessions, and a **Class Analytics Agent** that aggregates across a cohort. These are backend agents with their own prompts, meaning the assessment criteria, reporting format, and analytical focus are fully customizable per experience. The analytics agents work with the raw session data — transcripts, journals, artifacts — and produce reports that reference specific moments, identify patterns, and surface insights that no predefined rubric would have anticipated. The educator triggers analytics when ready and receives reports on individual students and the class as a whole.

## Designed for Expansion

The architecture is deliberately minimal at the platform level and maximal at the configuration level. The runtime provides communication infrastructure, tool execution, agent orchestration, resource management, and storage. Everything else — what agents say, how they behave, what they assess, what visual elements they create, how they coordinate — is defined in experience configurations and agent prompts.

This separation means the system's capabilities grow primarily through new experiences and templates, not through platform code changes. A new pedagogical approach requires a new template and new agent prompts, not new features in the runtime. A new tool extends every agent that includes it in its toolset. A new AI provider can be added as a named configuration and referenced by any agent. The platform is a stage; the experiences are the performances. The stage is built once and designed to accommodate performances that have not yet been imagined.
